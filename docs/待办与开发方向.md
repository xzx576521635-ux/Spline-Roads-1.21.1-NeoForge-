## 2. 已知问题

0. **Xaero 旧地图块不刷新（长路中间灰色）**
   - 现象：长路两端有树/路灯颜色，中间（飞过去、地图已加载后）仍是灰色；
   - 已确认**不是标记缺失**：testroad 中间区块实际标记数量与两端一致
     （z850-950:742、z1400-1500:701、z1500-1600:808、z1600-1700:508、z2150-2228:516）；
   - 原因：Xaero 只在地图块首次生成或收到方块变化时重画；中间区块首次生成地图时标记还没放上，
     之后没有方块变化，飞过去也不会重采样；
   - v54 尝试：区块加载时临时切换一个标记的 kind 再恢复，制造一次方块变化，促使 Xaero 重画整个区块；
     **效果待验证**（若只更新单个像素则无效）；
   - 后续可选方案：
     a. 若 v54 有效 → 保留；
     b. 若只更新单像素 → 需要区块级批量刷新（改动大、风险高）或调用 Xaero 内部重载/缓存清理（侵入性强）；
     c. 接受现状：新建道路在未探索区域首次进入即有颜色；旧灰色区域用 Xaero 地图缓存重置/重载解决；
   - 当前版本已可正常使用，**这项暂不改**，等以后有更好的办法再处理。

1. **VBO 后端不投影**
   - 手动 `/sr sf VBO` 时，桥/坡面在下方不产生阴影；terrain 后端正常。
   - 原因：VBO 几何是独立客户端网格，不进入 Iris shadow map；
     Iris 阴影贴图只包含区块烘焙几何（详见 `变更记录.md` §3.7）。
   - 现状：保持现状。默认 AUTO 在光影开启时走 terrain，正常玩法不受影响；
     DH 存在时 AUTO 强制 VBO，此时道路不投影是既有取舍。
   - 补充事实：本包没装 Immersive Engineering，Iris 在阴影通道根本不发
     `RenderLevelStageEvent`；即使有 IE，事件给的 modelView 是单位矩阵，不能直接画世界坐标几何。
     真要修只能 inject Iris `ShadowRenderer.renderShadows`。
2. **DH 粗模清理暂不可用**
   - 删除道路后 `road_marker` 仍会留在世界存档，DH/Xaero 会继续显示残影；
   - v36/v37 的批量清理导致区段清空事故，已回退；
   - 2026-11-15 对照实验（详见 `变更记录.md` v37 条目）结论：
     - C2ME 异步序列化**不是**原因（关掉照样坏）；
     - v37 的标记清理**是**触发条件（v35 同操作 0 损坏）；
     - 但“只删标记方块”为何会导致整段（含基岩）为空，机制仍不明。
3. **陡坡卡脚**（v16 的 1/8 格碰撞）
   - 低优先级，属于移动/相机手感，不影响稳定性。

## 4. Bug 定位记录（历史：旧路编辑后空洞）

- **v16**：用户确认**没有**此 bug（只做新路建造）。
- **v17**：第一次出现。
- **testB**（v16 + 允许清理 marker）：**无 bug**，新建道路正常。
- **testA**（v16 + 标记清理）：再次出现空洞；但存档检查发现：
  - 道路数据被编辑（3 号路端点改变）；
  - 空洞正好在**旧路被移除/改线**的区段；
  - 标记清理只删除 `road_marker`，不可能删除地形/路面；
  - testB 无清理 → DH 粗模应该还在；testA 有清理 → 粗模应消失。
  → **空洞来自旧路删除/restore，不是标记清理**。
- 结论：触发条件是**编辑/删除旧路**；v16 也有隐患，只是之前没做这类编辑。
- **v29 修复并验证通过**：
  - 禁止 clearance/air 清实体地形/基岩；
  - restore 缺 original 时恢复旧路 fill 材质，不再挖洞；
  - 碰撞/deck 兜底；
  - 不含标记清理（DH 粗模暂时保留）。

### 附：所有道路无碰撞 + 建路后区块范围清空（已修，v28/v29）

**现象**
- 垂直结构（灯杆、树干、龙门架腿）有碰撞；水平结构/路面没有；
- 旧道路也没碰撞；
- 新建道路会顶掉地表一层，随后道路和周围方块**按区块范围**消失，玩家下坠；
- 坐标示例：-231.947 / -58 / 124.411。

**根因**
1. `RoadIndex` 的 deck 数据/形状缺失时，`Road.getCollisionShape` 返回空；
   垂直结构有独立 box，所以只有它们有碰撞。
2. clearance/air 写入在 `air` 集合异常变大时仍会把实体地形写成空气，
   造成区块范围清空；`body` 覆盖异常时更明显。
3. 旧路 deck 会被重叠编辑的 restore 删除（v25/v26 已修）。

**v28 修复**
- `FILL=NONE` 的 road collider 在 `index.shape` 为空时返回**整块碰撞**；
- `repairChunk` 直接按道路 **mesh 采样**补 deck（不依赖 raster/cells），
  覆盖全宽（含中央带），放在道路表面所在方块格；兜底整块碰撞保证可站立；
- clearance/air 不再允许把**实体地形/基岩**写成空气（只允许 `body` 或旧道路替换）；
- 保留 v26 的 `stillOwned`：restore 不删除仍存在道路的 deck；
- 正常数据时仍使用 v16 的 1/8 格碰撞形状。

## 5. 新需求：道路尽头/边缘衔接（暂缓）

用户 2026-11-15 反馈：

- 道路尽头会出现**方块缺失/锯齿**；疑似与 v15“顶层 `FILL=NONE`、道路方块替换草方块”有关；
- 草方块与道路边缘之间出现缺口/悬空边，需要做成**道路尽头与地形平滑衔接**；
- 目标是道路端点/边缘不要出现一层草被顶掉后的空洞，能和草地/路肩自然接上。

已尝试并否决：

- v30：边界 1 格保留 fill → 草透路面；
- v31：边界 2 格 + 覆盖率 → 草透路面，侧边看穿未解决；
- 用户决定：**不做自动边缘衔接**，小缺口手动补。

如果以后重做，方向：**端帽/路肩几何**（端点和边缘生成收口几何），而不是改世界填充。

## 6. 后续方向一：适配生存（道路消耗等量方块）

目标：道路不再“凭空出现”；生存模式下建设道路需要消耗与工程量等量的方块/材料，
数量可以是成千上万。

需要进一步确认/设计：

1. **消耗范围**
   - 只算路面表层，还是包含路基填充、路肩、人行道、护栏、路灯、树木、花坛等结构？
   - 不同道路样式（宽度、厚度、桥梁/隧道）消耗不同；装饰性结构是否单独计价。
2. **材料匹配**
   - 按道路实际使用的调色板/方块类型扣除（沥青块、石材、混凝土、树叶、灯具等）；
   - 是否允许用等价材料替代；消耗物品/方块本身，还是“材料点”。
3. **库存来源**
   - 玩家物品栏、附近容器、ME/存储网络、创造模式豁免；
   - 多人服务器权限/领地/经济插件兼容；
   - 材料不足时：拒绝建造 / 只建一部分 / 排队等待。
4. **事务与回滚**
   - 先检查再扣料，建造失败/取消/服务器异常时完整退回；
   - 删除/修改道路是否返还材料（按比例？）；防止刷物品/复制。
5. **性能**
   - 大型道路一次消耗数万方块，不能逐格发 packet；
   - 批量合并消耗、按调色板统计、服务端权威计算；
   - 与 `RoadData` 的 `PreparedEdit`/调色板数据结构结合。
6. **配方/工具成本**
   - 现有工具已有合成表；是否需要提高工具成本/耐久；
   - 生存前期是否允许低成本土路，后期高成本沥青/桥梁。

技术切入点（供实现参考）：

- `RoadData` 的建造/编辑提交（`PreparedEdit`、`setBlock` 前的准备数据）；
- `RoadBlockStorage`/调色板与 `RoadFillEntity`；
- `RoadIndex`/`RoadRaster` 统计工程量；
- 服务端 `ServerPlayer` 库存与容器扫描；
- 事务层：先预留/扣除，成功后提交；失败回滚；
- 客户端 UI 显示预计消耗、材料是否足够。

## 7. 后续方向二：更好的建造方式（类似机械动力火车轨道）

目标：类似 Create 火车轨道/MTR 的建造体验：

1. 放下一个道路端点；
2. 用道路连接器右键选择该端点；
3. **先出现道路设置 UI**，配置样式/宽度/车道/桥梁/绿化等；
4. 配置完成后，出现一条类似 MTR 的**文字 + 线条**预览；
5. 预览跟随玩家前进/后退而定位、延长/缩进；
6. 实时显示道路长度、弯度、方向等信息；
7. 确认后建造。

当前原 mod 的问题：

- 想建直线需要玩家自己走得很直；稍微偏一点，路就弯；
- 放置端点后没有“先配置再预览”的阶段；
- 预览/长度信息不直观。

设计要点：

1. **固定端点/方向**
   - 先确定起点与终点/方向，而不是完全跟随玩家当前位置；
   - 支持“直线模式”“固定切线/角度”“曲线半径”；
   - 滚动/按键延长/缩进终点，同时保持起点不变。
2. **预览会话（客户端）**
   - `RoadPlanSession`：起点、方向、长度、样式、预览几何、消耗估算；
   - 复用现有 `ClientRoads.preview` / `RoadGeometry` / `RoadPlanner` / `RoadScreen` 配置；
   - 实时生成 `RoadRenderMesh` 预览；线条 + 文字使用世界渲染（类似 MTR 的线路/长度标注）。
3. **交互**
   - 右键节点进入配置；滚轮/按键调整长度、方向、弯度；
   - 确认/取消/撤销；预览中显示材料消耗（配合生存方向）。
4. **服务端权威**
   - 客户端只做预览；确认后把最终计划发给服务端；
   - 服务端校验材料、权限、碰撞、占用，再执行建造；
   - 多人同步与包体大小控制。
5. **UI**
   - 配置界面在放置端点后先出现，而不是建完才改；
   - 提供“直线/曲线/角度/半径/样式/材料”等参数；
   - 实时显示长度、弯度、预计方块数、材料清单。

技术风险：

- 预览跟随玩家移动需要每 tick 重建几何，需限制预算/缓存；
- 端点固定与玩家朝向的坐标转换要明确；
- 服务端与客户端预览一致性；
- 大量预览几何/文字渲染性能；
- 与现有道路编辑、连接器、节点、删除/撤销逻辑的兼容。

## 8. 发布形态

用户希望最终是**独立 mod**，可以放到任何兼容客户端（安装相应前置 mod 也能用），
并兼容其他 mod。因此：

- 保持 DH/Xaero 为可选集成，不引入硬依赖；
- 新功能尽量不依赖整合包专用类；
- 生存消耗、建造预览等大功能可以考虑做成**附属 mod**，但核心 API/数据格式要稳定；
- 每次版本继续独立备份（`.vN`），不再覆盖旧版本；
- 渲染机制改动前先读 `变更记录.md` 第 3 节检查清单。

### 能否直接“跟上”

不能直接把 1.20.1 Forge 的 2.1.0 放进本客户端：

- 我们的版本是 **1.21.1 NeoForge 移植 + 大量自定义兼容/修复**（Sodium、Iris、DH、
  Xaero、标记方块、渲染状态修复）；
- 1.20.1 Forge 与 1.21.1 NeoForge 的注册、模型、事件、映射 API 不同；
- 直接替换会丢失现有所有兼容修复，并可能无法启动。

### 建议策略
